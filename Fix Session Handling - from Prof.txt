# Fix Session Handling — GET/POST and Multiple Login Conflicts

Inspect and fix the existing authentication/session implementation of the application.

The main issue appears to be related to **session state being incorrectly shared, detected, retrieved, or updated when multiple users log in through the same login page**.

Do not completely replace the existing authentication system unless absolutely necessary. First inspect the current implementation and identify exactly how the session is created, retrieved, updated, and destroyed.

## 1. Main Problem

The application must support multiple users logging in through the same login page without their sessions interfering with each other.

Example problem:

```text
User A logs in
↓
User A receives Session A
↓
User A logs out
↓
User B logs in through the same login page
↓
System incorrectly detects an old/active session
or retrieves the wrong session state
↓
Login/session behavior becomes inconsistent
```

The system must ensure that **each authenticated login has its own independent session**.

One user's login/logout must never affect another user's session.

---

# 2. Inspect the Existing Session GET Logic

Review every place where the application performs a GET/read operation related to authentication or sessions.

Check:

* How the current Session ID is retrieved.
* Where the session cookie is read.
* How the session is queried from the database/session store.
* Whether the session is being retrieved using the correct Session ID.
* Whether the session is incorrectly retrieved using only a User ID.
* Whether a global/shared session variable is being used.
* Whether cached session information is being reused between users.
* Whether stale session information is returned after logout.
* Whether the frontend is using old authentication/session state.

The GET operation must always retrieve the session associated with the **current request's authenticated session identifier**.

Do not return another user's session.

---

# 3. Inspect the Existing Session POST Logic

Review every POST operation that creates, updates, or destroys sessions.

Pay particular attention to:

* Login
* Logout
* Session creation
* Session refresh
* Session activity updates
* Session expiration
* Session revocation

Make sure POST operations modify **only the session belonging to the current authentication request**.

Do not use a shared/global session record for all users.

---

# 4. Login Session Creation

When a user successfully logs in:

```text
Login Request
    ↓
Validate Credentials
    ↓
Create NEW Session
    ↓
Generate UNIQUE Session ID
    ↓
Store Session
    ↓
Set Session Cookie
    ↓
Return Authenticated Response
```

Every successful login must receive its own unique Session ID.

For example:

```text
User A → Session A
User B → Session B
User C → Session C
```

Do not reuse:

```text
User A → Session 1
User B → Session 1
User C → Session 1
```

unless the existing architecture explicitly requires that behavior and securely isolates users.

---

# 5. Do Not Use a Global Session

Search the codebase for patterns such as:

```text
global session
shared session
currentUser
currentSession
authenticatedUser
```

or server-side variables that store the currently logged-in user globally.

Do not store the authenticated user/session in a global server variable that can be shared between requests.

For a multi-user web application, authentication state must be associated with the **individual request/session**, not with the entire server process.

---

# 6. Session Identification

The server must identify the current session using the session identifier supplied by the current request.

The flow should be:

```text
Browser Request
      ↓
Session Cookie
      ↓
Extract Session ID
      ↓
Find Session by Session ID
      ↓
Find Associated User
      ↓
Validate Session
      ↓
Authorize Request
```

Do not identify the session solely by:

```text
IP address
Browser
Device
Username
Email
User ID
```

These values may be useful as additional metadata, but the Session ID must uniquely identify the authenticated session.

---

# 7. Logout Handling

Fix the logout process so that it destroys/revokes the **correct session only**.

When User A logs out:

```text
User A
Session A
   ↓
Logout
   ↓
Revoke Session A
```

It must NOT:

```text
Revoke Session B
Revoke all users' sessions
Modify User B's authentication state
Modify User C's authentication state
```

After logout:

```text
Session A → Invalid
Session B → Still Valid
Session C → Still Valid
```

unless the user explicitly chooses a "Logout All Sessions" feature.

---

# 8. Clear the Session Cookie Correctly

When logging out:

1. Revoke/destroy the server-side session.
2. Clear the browser's session cookie.
3. Ensure the cookie is cleared using the same relevant cookie attributes/path/domain used when it was created.
4. Do not leave an old Session ID available to the browser.

The old Session ID must no longer authenticate the user.

---

# 9. Prevent Stale Session Detection

Fix situations where the application thinks:

> "This user is still logged in"

even though the user has already logged out.

When checking whether a user is logged in:

```text
GET Session
    ↓
Session exists?
    ↓
Session revoked?
    ↓
Session expired?
    ↓
User still active?
```

Only consider the user authenticated if all required checks pass.

For example:

```text
Session exists = true
AND
Revoked = false
AND
Expired = false
AND
User active = true
```

Otherwise, the session must be treated as invalid.

---

# 10. Avoid User-ID-Only Session Checks

Pay special attention to code similar to:

```text
findSessionByUserId(userId)
```

or logic that assumes:

> One user = one global session

If the application allows multiple logins/devices, a user may have multiple valid sessions.

Instead, session operations should normally be based on the specific Session ID:

```text
findSessionBySessionId(sessionId)
```

Then retrieve the associated user.

If the system intentionally supports only one active session per user, implement that rule explicitly and safely rather than accidentally producing it through session conflicts.

---

# 11. Multiple Users Using One Login Page

The login page itself must be completely stateless with respect to individual users.

Example:

```text
                LOGIN PAGE
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
    User A        User B        User C
       ↓            ↓            ↓
  Session A     Session B     Session C
```

The fact that all users use the same:

```text
/login
```

page must not cause them to share a session.

The login page must not store a shared:

* Current User
* Current Session
* Logged-in User
* Session ID
* Authentication state

on the server globally.

---

# 12. GET and POST Must Use the Same Session Context

Ensure that session-related GET and POST requests correctly use the authenticated session associated with the current browser.

Example:

### GET

```text
GET /api/session
Cookie: session_id=ABC
        ↓
Return Session A
```

### POST

```text
POST /api/logout
Cookie: session_id=ABC
        ↓
Revoke Session A
```

A different browser:

```text
GET /api/session
Cookie: session_id=XYZ
        ↓
Return Session B
```

The server must never confuse `ABC` and `XYZ`.

---

# 13. Prevent Session Race Conditions

Check for race conditions where multiple requests happen at nearly the same time.

For example:

```text
Request A → Login
Request B → Logout
Request C → Get Session
```

Make sure the final session state is consistent.

Session creation, update, and revocation should be handled atomically where necessary.

Avoid situations where:

```text
Logout succeeds
but
GET /session still reports the user as logged in
```

because of stale or cached session data.

---

# 14. Frontend Session State

Inspect the frontend authentication state as well.

Make sure the frontend does not continue displaying a user as logged in after the server has invalidated their session.

After logout:

* Clear the frontend authentication state.
* Clear cached user/session data.
* Clear relevant query/cache state.
* Redirect to the login page.
* Prevent protected pages from continuing to display stale user information.

However, the **server must remain the authoritative source of authentication state**.

---

# 15. Session API Requirements

Review the existing session endpoints and make sure they behave correctly.

For example:

### GET Session

```text
GET /api/session
```

Expected behavior:

```text
Valid Session
→ Return the authenticated user's session information.

Invalid/Expired/Revoked Session
→ Return 401 Unauthorized.
```

### POST Login

```text
POST /api/login
```

Expected behavior:

```text
Valid Credentials
→ Create a new unique session.

Invalid Credentials
→ Reject authentication.
```

### POST Logout

```text
POST /api/logout
```

Expected behavior:

```text
Valid Session
→ Revoke that specific session.
→ Clear session cookie.

Invalid/Already Logged Out
→ Safely return an appropriate response.
```

Use the application's existing endpoint names if they are different.

---

# 16. Session Data Isolation

Verify that session data is isolated between users.

For example:

```text
User A:
userId = A
sessionId = SESSION_A

User B:
userId = B
sessionId = SESSION_B
```

User A must never receive:

```text
userId = B
```

and User B must never receive:

```text
userId = A
```

Also verify that API responses, cached data, database queries, and frontend state are properly scoped to the authenticated session/user.

---

# 17. Caching Problems

Inspect whether session/user API responses are being cached incorrectly.

A response containing authenticated user information must not accidentally be reused for another user.

Review:

* Browser cache
* API cache
* React/query cache
* Server cache
* CDN cache
* Redis/session cache, if used

Authenticated session responses should be correctly scoped and should not be publicly/shared cached.

---

# 18. Do Not Break Existing Roles and Permissions

After fixing the session system, all existing authorization rules must continue working.

A valid session only proves:

> "This user is authenticated."

The existing authorization system must still determine what the user can access.

Preserve existing access rules for:

* Students
* Institution Staff
* Institution Main Account
* Organization Staff
* Organization Main Account
* Administrators
* Assigned Programs/Departments
* Degree Programs
* OJT records
* DTR
* Evaluations
* Requirements
* Career Portfolio
* Digital Credentials

# 19. Testing Scenario

After implementing the fix, test the exact multi-login scenario.

### Test 1 — User A

```text
Open Login Page
↓
Login as User A
↓
Verify Session A
↓
Access Dashboard
↓
Logout
↓
Verify Session A is invalid
```

### Test 2 — User B

```text
Same Login Page
↓
Login as User B
↓
Verify Session B
↓
Access Dashboard
```

Confirm that User B does not inherit User A's session.

### Test 3 — Simultaneous Users

Open separate browsers/incognito windows:

```text
Browser 1 → User A → Session A
Browser 2 → User B → Session B
Browser 3 → User C → Session C
```

Verify:

```text
User A sees User A data
User B sees User B data
User C sees User C data
```

Then:

```text
User A logs out
```

Verify:

```text
Session A → Invalid
Session B → Still Valid
Session C → Still Valid
```

---

# 20. Final Requirement

**Focus the fix on the existing session GET and POST implementation.**

Do not solve the problem by simply hiding the issue on the frontend.

Find and fix the underlying cause of:

* Incorrect session retrieval
* Incorrect session creation
* Incorrect session updates
* Incorrect session deletion
* Stale session detection
* Shared/global session state
* Session ID reuse
* Incorrect cookie handling
* Cached authentication state
* Race conditions
* Multiple users interfering with each other's sessions

The final system must support:

```text
Same Login Page
      ↓
Multiple Users
      ↓
Independent Sessions
      ↓
Independent GET Requests
      ↓
Independent POST Requests
      ↓
Independent Logout
      ↓
No Session Conflicts
```

**Primary goal: Fix the existing session handling, especially the GET and POST operations, so multiple users can use the same login page safely without their login/logout/session states interfering with one another.**
